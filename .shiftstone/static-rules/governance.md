# {{PROJECT_NAME}} — Harness-as-Code Governance (B11)

The **harness** — `AGENTS.md` and the IDE shims, `.shiftstone/static-rules/`,
`.shiftstone/path-scoped-rules/`, `evals/`, and skills
(`.agents/skills/` + `packs/<pack>/skills/`) — is production infrastructure,
not notes. It is PR-reviewed, versioned, and has named owners (Osmani 06,
leader rec #1/#5).

1. **Pull request with checklist.** Harness files change only via PR. The PR
   description (or, in a solo repo, the commit body) must tick:
   - [ ] `pnpm parity` and `pnpm typecheck && pnpm test` pass
   - [ ] `pnpm manifest` re-run if any skill changed (manifest + AGENTS.md index are generated)
   - [ ] Why this harness change is needed (one sentence)
   - [ ] Evidence: the gate, test, or eval that proves it behaves as claimed
2. **Named owners.** `CODEOWNERS` (repo root) names the maintainer for every
   harness path; GitHub requests their review on any PR touching those paths.
   `node .shiftstone/scripts/check-harness-ownership.js --strict` fails CI when the
   file goes missing or stops covering a harness path.
3. **Solo degrade.** In a one-maintainer repository there is no second
   reviewer: the owner is the maintainer and the rule degrades to the
   self-review checklist above — the checklist is still mandatory, never
   skipped because "only I touched it".
4. **Generated files are not hand-edited.** `.shiftstone/context/skills-manifest.yaml`,
   the AGENTS.md Skill INDEX block, `docs/**/index.md`, and the bible README
   ToC are regenerated by their generators; the PR checklist includes a fresh
   run of those generators.

The ownership table lives in the root `README.md` (§ Harness Ownership).
