# User Taste Profile
- Plans/blueprints authored FOR the framework live in the project's `docs/plans/` (not in `~/.commandcode/plans/` or any outside-of-repo location). Confidence: 0.95
- Empty `docs/*` subdirectories in a starter framework are intentional, not bugs. They get populated as the framework is used for a real project. Confidence: 0.95
- When asked to declare the purpose of a directory, prefer "ship a README declaring purpose + template" over "populate with example content." The empty starter state is the correct starter state. Confidence: 0.9
- Never delete a `docs/*` directory whose purpose is unclear; instead flag it as an open question for human decision. Confidence: 0.95
- `.commandcode/taste/taste.md` is empty BY DESIGN in a new project. It is populated automatically by the Command Code taste-learning system as the AI agent learns preferences during development. The framework must NOT pre-populate, manually edit, or "fix" this empty file — doing so corrupts the learning signal. Confidence: 0.95
- Add explicit "do not pre-populate" notes in steering rules (AGENTS.md, COMMANDCODE.md) for files that the taste-learning system owns. Confidence: 0.85
- Engages substantively with multi-choice architectural questions (each branch answered decisively in one message). Prefers being asked specific architectural forks via `ask_user_question` over open-ended discussion. Confidence: 0.9
- Pushes back when an agent misframes something as a gap. Prefers accurate diagnostic framing (e.g., "empty dirs in a starter are by design" vs "these need to be filled or deleted"). Confidence: 0.9
- Favored resolutions: Hybrid Loop+ICM workflows (loops drive ICM stages), Two-layer Core+Packs architecture with flagship archetype, Hard-enforced maker-checker with Two-Gear verification boundary, Full universal refactor (not incremental). Confidence: 0.9
- `docs/plans/` — implementation plans from AI agents (hybrid Loop+ICM artifacts with numbered folders + CONTEXT.md stage contracts). Confidence: 0.9
- `docs/roadmap/` — long-form development roadmap (milestones, PRDs, quarterly themes, higher-level than backlog). Confidence: 0.9
- `docs/reports/` — publication-grade outputs: AI audits, research summaries, performance reports, ad-hoc investigations requested by developer. The "papers" folder. Confidence: 0.9
- `docs/status-reports/` — current development status snapshots (timestamped, typically regenerated by `/status` workflow). Confidence: 0.9
- `docs/sync-reports/` — purpose DECIDED (user approved the plan resolving it): **Candidate C — cross-source sync receipts** (any sync of two sources of truth emits a receipt; primary use case = drift-detection outputs from `/sync-bible`, `/schema-sync`). Confidence: 0.85
- `docs/bugs/` — known bugs ledger; permanent, never delete. Managed by `/bug-report` workflow. Confidence: 0.95
- Every steering rule file (AGENTS.md, ANTIGRAVITY.md, CLAUDE.md, COMMANDCODE.md) should include a "Documentation Directory Map" section referencing the canonical purpose registry so AI agents answer "where does X go?" by reading one file. Confidence: 0.85
- Preserves decision provenance as separate audit-trail files. When the agent asks clarifying questions, the user later asks for the Q&A to be saved as a standalone markdown file (e.g., `docs/temp/blueprint-planning-questions.md`) rather than only embedded in the plan. Confidence: 0.9
- Plan-before-execute workflow for major work: explicitly says "I don't want you to update [the artifact] yet — first create a plan" and gates implementation behind an explicit approval ("Implement the plan"). Never mutate the main artifact until the plan is approved. Confidence: 0.9
- Scopes each work session to one explicitly named plan file (e.g., "continue implementing the meta-plan `blueprint-gap-analysis-phase-planning.md`") and wants that plan carried to full completion — including its built-in verification checklist and status updates — before any downstream work (e.g., actual code/boilerplate phases) begins. Distinguishes sharply between a *meta-plan* (plan that updates the blueprint/plan artifacts) and the *implementation plan* (real code); they must not be conflated or skipped ahead. Confidence: 0.8
- Big tasks must be divided into sequential phases, with **one separate Markdown plan file per phase** so implementation proceeds one phase at a time; the related blueprint/plan gets its own dedicated subfolder under `docs/plans/` to hold it plus the per-phase files. Confidence: 0.9
- Prefers descriptive kebab-case filenames for records saved in `docs/temp/` (e.g., `blueprint-planning-questions.md`). Treats `docs/temp/` as a valid location for working/draft/decision-record artifacts. Confidence: 0.8
- When plan files already exist ("We have already created the plan files so there is no need to create a new plan"), skip plan creation entirely and go straight to implementing the named phase. Never generate redundant/duplicate plans over existing ones. Confidence: 0.75
- After finishing phases (e.g., Phase 1 + Phase 2, then Phase 3 → Phase 4), requests a full verification audit before starting the next phase: check the whole implementation for gaps, misalignments, and other issues, fix any found on the spot, and explicitly confirm readiness to start the next phase. Wants defects repaired during the audit, not merely reported. Repeated ritual at every phase boundary, and it extends to numbered workstreams: e.g. "Verify the implementation of WS-A and WS-B ... if you find any I want you to fix them then implement WS-C" — several completed workstreams audited in a single pass (gaps, misalignments, any other issues), defects fixed on the spot, then the next workstream starts. Confidence: 0.9
- Before implementing a phase, first build full context by reading the entire plan folder — index/README, the target phase's plan, the prior phases' plans, and relevant blueprint sections — and surveying what's already built in the codebase. Only after "full context" should implementation of the named phase begin; no separate approval gate is required when the plan files already exist. Confidence: 0.8
- Implements each phase in a separate chat with a fresh agent (prompt: "go through the plan files, understand the plan, implement Phase N"). Wants the plan folder's first-read file (README.md, since index.md is machine-generated) to carry an explicit "AI reading protocol" telling agents exactly which files to read in what order before implementing a phase — so agents don't waste context on the full blueprint or get confused by already-implemented artifacts (e.g., resolved gap/amendment files). Thinks about documentation's ergonomics for future AI readers. Confidence: 0.85
- When an opaque system/agent error appears (e.g., "The request was rejected because it was considered high risk"), asks for a concrete explanation before letting work continue — wants what happened, whether anything was actually written, the likely trigger, and the proposed fix. Confidence: 0.7
- When a long phase implementation stalls or hits a context boundary mid-run, resumes with a single bare "continue" (or a one-line "Was everything in phase N implemented? If not then continue" after an interruption such as a rejected tool call) and expects the agent to pick up exactly where it left off from its own tracked progress (todo list / last completed task) — no recap, no re-confirmation, no re-asking what to do next. Confidence: 0.8
- Delegates git to the agent: after an audit/fix pass, explicitly asks the agent to "make another git commit for pushing all these changes to github" — fixes should land as their own commit, leaving the tree clean and push-ready, rather than being left uncommitted or handled manually by the user. Confidence: 0.75
- For whole-plan audits, specifies the exact methodology up front: (1) read the plan files carefully FIRST, (2) compare the plan against the actual workspace implementation, (3) run a deep audit for gaps, misalignments, and other issues, (4) only then produce a detailed implementation plan that fixes every found gap — no ad-hoc fixing during discovery. Confidence: 0.85
- When a skill or capability must be provisioned, prefers installing it fresh from its canonical upstream source (e.g., `npx skills add` from skills.sh) over reusing an existing local/ad-hoc copy, then adapting the installed content to workspace conventions. Confidence: 0.7
- Dispatches work with one-line imperatives referencing a pre-planned, numbered workstream ID (e.g., "Impliment WS-B"), expecting the agent to retrieve the workstream's definition from the existing plan files itself, execute it end-to-end (including its built-in verification gates), and report back — no restating of requirements, no re-confirmation, no mid-run approval checkpoints. Confidence: 0.7
- When CI (GitHub parity) fails after a push, pastes the full structured failure summary — failure, root cause, log location, and any non-fatal warnings — and expects the agent to find and fix ALL reported issues, not just the failing test: secondary warnings (e.g., pnpm ERR_PNPM_IGNORED_BUILDS) should be resolved in the same pass, then everything re-verified locally. Confidence: 0.7
